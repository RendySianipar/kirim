# ADR 0006: Kubernetes manifests with Kustomize, delivered by GitLab CI

**Status:** accepted

## Decision
- Plain Kubernetes YAML in `deploy/k8s/base`, with **Kustomize overlays** (`local` for kind, `gitlab` for the CI deploy). No Helm: there is one app and two environments, and plain manifests are easier to review.
- The API runs **2 replicas**, which the design already allows (outbox `SKIP LOCKED`, Redis-shared rate limits, Kafka consumer groups). A `PodDisruptionBudget` keeps one pod during node drains; rolling updates use `maxUnavailable: 0`.
- Probes use Spring Boot's liveness/readiness groups. A **startup probe** covers JVM start and Flyway migrations, so slow starts don't trigger restarts.
- Containers run as non-root with a read-only root filesystem (`/tmp` is an `emptyDir`) and no Linux capabilities.
- Secrets are generated by Kustomize from **development-only** literals. A real cluster would use a secret manager (External Secrets, Sealed Secrets, Vault).
- PostgreSQL, Kafka and Redis run in-cluster as single instances for development. Production would use managed services or operators (CloudNativePG, Strimzi) with replication.

## GitLab CI
- `test`: both Gradle builds with Testcontainers on Docker-in-Docker, the web build, and a manifest render check.
- `build` (default branch): Docker images tagged with the **commit SHA**, pushed to the GitLab Container Registry.
- `deploy` (manual): via the GitLab agent for Kubernetes. The job pins the overlay to this commit's images, applies it, and waits for `rollout status`, so a crash-looping release fails the pipeline.

## Consequences
- Rollback = re-run the deploy job of an earlier pipeline (images are immutable SHA tags).
- GitHub Actions stays as the CI for the GitHub mirror; both pipelines run the same Gradle and npm commands.
